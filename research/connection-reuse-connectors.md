# Connection reuse: OpenMetadata and Airbyte

Research checked 2026-09-17 against official documentation and repositories. This is a capability assessment, not an architecture recommendation. Documentation on moving `main`/`master` branches must be rechecked against any version selected for implementation.

## Findings that change the discussion

1. **Connection configuration APIs exist; credential export is a separate capability.** Airbyte exposes `GET /v1/sources/{sourceId}`. Its update documentation explicitly says fields marked `airbyte_secret: true` are not returned by GET; the masked placeholder preserves existing secrets on update. Therefore an authorized importer can retrieve supported settings, but cannot assume it can obtain usable passwords or tokens. [Get source](https://reference.airbyte.com/reference/getsource), [update source and secret masking](https://reference.airbyte.com/reference/putsource).
2. **Correction: OpenMetadata's root Apache 2.0 license does not cover the current ingestion framework uniformly.** Its `ingestion/LICENSE` and inspected PostgreSQL, Db2, and S3 connector headers specify the Collate Community License. The earlier statement treating these connectors as Apache 2.0 was incorrect. Current ingestion code does not meet an MIT/Apache-only baseline. Airbyte's current license page says public repositories/connectors use ELv2, except `airbyte-protocol`, which is MIT; commercial offerings have separate licenses. Individual pinned artifacts and third-party drivers need separate checks. [OpenMetadata ingestion license](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/LICENSE), [PostgreSQL connector header](https://github.com/open-metadata/OpenMetadata/blob/main/ingestion/src/metadata/ingestion/source/database/postgres/connection.py), [Airbyte licenses](https://github.com/airbytehq/airbyte/blob/master/docs/community/licenses/README.md). See the [follow-up feasibility investigation](connection-reuse-openmetadata-feasibility.md).
3. **Metadata connectors and replication connectors provide different read contracts.** OpenMetadata models a service connection and metadata workflows. Airbyte specifies `spec`, `check`, `discover`, and `read`: discovery describes streams and column schemas; reads emit records and replication checkpoint state. That can extract live source data, but is not evidence of an interactive SQL or Arrow Flight query interface. [OpenMetadata service creation](https://docs.open-metadata.org/v1.12.x/api-reference/data-assets/database-services/create), [Airbyte protocol](https://github.com/airbytehq/airbyte/blob/master/docs/platform/understanding-airbyte/airbyte-protocol.md).

## OpenMetadata

- The official connector inventory lists BigQuery, Db2, Oracle, PostgreSQL, Redshift, Snowflake, and both S3 Datalake and S3 Storage. This establishes metadata coverage, not equivalent functionality across sources or production validation in our environment. [Connector inventory](https://docs.open-metadata.org/latest/connectors).
- A service holds typed connection settings and is reused by ingestion workflows. The creation API accepts service-specific `connection.config`; the Python SDK also demonstrates retrieved service objects with connection fields. This supports programmatic registration/configuration reuse. The SDK's printed masked password example alone does **not** establish whether an authorized API caller can retrieve plaintext credentials: exact secret behavior and permissions remain to be verified in the selected release. [Create service](https://docs.open-metadata.org/v1.12.x/api-reference/data-assets/database-services/create), [Python SDK](https://openmetadata.mintlify.app/v1.11.x/sdk/python/index).
- OpenMetadata's secrets-manager design explicitly separates service references from secret storage. Its workflows resolve service information instead of requiring every workflow to duplicate connection details. External secret stores can hold sensitive values. [Secrets-manager design](https://docs.open-metadata.org/latest/deployment/secrets-manager).
- Kubernetes secret support is documented with a configurable namespace, server read/write RBAC, ingestion read-only RBAC, and deterministic OpenMetadata-specific secret names. This is relevant to OpenShift, but does not prove automatic compatibility with arbitrary pre-existing Kubernetes Secret names/shapes. The overview still describes some implemented stores as future work, so use release-specific implementation docs. [Kubernetes secrets implementation](https://docs.open-metadata.org/v1.11.x/deployment/secrets-manager/supported-implementations/kubernetes-secrets-manager).
- Db2 needs an additional ingestion package rather than relying on the default image. The documentation also identifies IBM client licensing considerations for some Db2 variants. The exact target matters: LUW, z/OS, and IBM i are not interchangeable deployment assumptions. [Db2 connector](https://docs.open-metadata.org/connectors/database/db2).
- S3 Storage is a distinct connector from S3 Datalake. Match the storage connector's bucket/container metadata behavior to the desired initial object discovery, rather than assuming database-style column discovery applies to PDFs. Full arbitrary document/object coverage was not validated here. [S3 Storage](https://docs.open-metadata.org/latest/connectors/storage/s3).
- No reviewed source establishes OpenMetadata as a general live-data query gateway or Arrow Flight server. Its ability to connect for profiling and metadata scanning must not be mistaken for that product contract. This is a scope inference, not a claim that its underlying drivers cannot execute queries.

## Airbyte

- Relevant source connectors exist, including warehouse **sources**, not just destinations: [Snowflake](https://docs.airbyte.com/integrations/sources/snowflake), [BigQuery](https://docs.airbyte.com/integrations/sources/bigquery), [Redshift](https://github.com/airbytehq/airbyte/blob/master/docs/integrations/sources/redshift.md), [Db2](https://docs.airbyte.com/integrations/sources/db2). The official license announcement also identifies PostgreSQL, Oracle, and S3 source connectors. [Source licensing inventory](https://airbyte.com/blog/update-on-airbytes-license).
- The source protocol reuses the same configuration across check, discovery, and record extraction. Its catalog contains streams with JSON schemas; relational tables map to streams and columns to schema properties. These are useful discovery primitives, distinct from a rich governance catalog. [Protocol](https://github.com/airbytehq/airbyte/blob/master/docs/platform/understanding-airbyte/airbyte-protocol.md).
- Connectors can be invoked as container commands without a complete platform deployment. Platform connector operations run in workload pods. This establishes a container/Kubernetes execution model; OpenShift SCC, arbitrary UID, resource use, egress, and image certification have not been tested. [Container protocol](https://github.com/airbytehq/airbyte/blob/master/docs/platform/understanding-airbyte/airbyte-protocol-docker.md), [workloads](https://github.com/airbytehq/airbyte/blob/master/docs/platform/understanding-airbyte/jobs.md).
- Airbyte documents AWS Secrets Manager, Google Secret Manager, Azure Key Vault, and HashiCorp Vault backends. On connector creation it writes/reads secrets through the configured manager. This is not a promise that it can bind any existing customer's secret reference without migration. Its deployment guide warns that changing backend configuration breaks existing connectors until they are recreated. Feature availability needs checking for the selected edition/version. [Secret management](https://github.com/airbytehq/airbyte/blob/master/docs/platform/deploying-airbyte/integrations/secrets.md).

## Open questions for a later implementation investigation

- Which exact OpenMetadata version and connector packages fit OpenShift deployment constraints?
- Can the selected OpenMetadata API expose authorized connection details and secret references in a stable, supported form? Which operations require elevated catalog permissions?
- What mappings are required between each external service's configuration and the notebook's native client parameters?
- Does discovery need to enumerate every S3 object, or only buckets and selected prefixes?
- Which Db2 platform/version is required, and what driver redistributability applies?
- A shared initial connection identity remains a deliberate simplification: these projects' connection reuse does not by itself preserve Alice's individual source entitlements.
