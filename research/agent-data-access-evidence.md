# OpenShell evidence for enterprise agent data access

Checked 2026-09-14 against NVIDIA's live documentation, labelled **Latest v0.0.116**. These are documentation findings, not deployment tests or a production support commitment. Pin and validate the release before implementation. Short source excerpts are cached in [sources/openshell-excerpts.md](sources/openshell-excerpts.md); that file is not a full snapshot.

## Documented capabilities

- **Trust boundary:** the gateway owns control-plane configuration and lifecycle; the supervisor inside the sandbox workload restricts the agent process and handles runtime enforcement. Credentials may reach this trusted supervisor without reaching the agent. Dynamic configuration travels through the authenticated gateway–supervisor relationship. [Architecture](https://docs.nvidia.com/openshell/about/how-it-works).
- **HTTP credentials:** agents receive placeholders, resolved by the proxy at approved endpoints. Non-HTTP tunnels and TLS inspection bypass do not support credential rewriting. Basic authentication, configured HTTP body rewriting, and AWS SigV4 signing are documented; generic PostgreSQL wire-protocol rewriting is not. External refresh systems can push replacement values through `provider update`. [Providers](https://docs.nvidia.com/openshell/sandboxes/manage-providers).
- **Provider policy and refresh:** Providers v2 offers custom profiles, provider attachment, endpoint credential bindings, gateway-managed refresh, and dynamic token grants using sandbox SPIFFE JWT-SVID assertions. Gateway-managed access-token rotation can preserve a stable placeholder in a long-running process. Reconfiguration and detachment have different revocation semantics. Expiry enforcement is documented. This is not automatic discovery of upstream permission scopes, which remains a roadmap item. [Providers v2](https://docs.nvidia.com/openshell/sandboxes/providers-v2).
- **Secrets/Vault integration exists:** built-in `kubernetes-secrets` and `vault` drivers store OpenShell-managed provider credentials. Only one external credential driver may be enabled. Provider create/update submits secret values and persists backend handles. Vault supports Kubernetes authentication. These documented storage operations do not establish automatic consumption or watching of arbitrary pre-existing customer Secret objects or Vault paths. [Gateway configuration](https://docs.nvidia.com/openshell/reference/gateway-config).
- **Sidecar option:** Kubernetes can separate pod network enforcement/gateway access into a sidecar, leaving the agent container without added Linux capabilities. The default sidecar configuration still has privileged duties; it is not proof that the whole pod fits a restricted OpenShift SCC. [Compute drivers](https://docs.nvidia.com/openshell/reference/sandbox-compute-drivers).
- **OpenShift maturity:** upstream calls the installation experimental and requires a privileged SCC for sandbox pods. Its introductory evaluation instructions disable gateway TLS, but a later section provides TLS, cert-manager, Route, and OIDC configuration. Do not infer that TLS is universally unsupported, or that the later section establishes production readiness. [OpenShift](https://docs.nvidia.com/openshell/kubernetes/openshift).

## Design consequences and proposals—not upstream guarantees

1. Bind each agent process to its defined user or approved workload principal, then authorize source-specific provider/account mappings. OpenShell's gateway identity and sandbox identity do not automatically become the correct Snowflake/PostgreSQL user.
2. Use an existing suitable HTTP source API/tool service directly through the policy proxy. When a source needs native authentication, place a trusted adapter outside the agent process; it authenticates the agent process and uses the approved source account. Reuse existing customer services first. MCP is a possible tool interface, not an identity mechanism or universal requirement.
3. Treat customer Secret/Vault references, provider provisioning, and refresh/revocation propagation as an integration contract to design. Reuse documented drivers and refresh features where they fit. Do not promise that editing a Secret immediately changes active proxy credentials or existing database sessions.
4. Distinguish source credential rotation, source client-certificate renewal, and OpenShell gateway/supervisor TLS renewal. The inspected provider docs do not establish a universal mechanism that hot-reloads all three. Agree propagation bounds and test stale credentials, backend outage, and revocation.
5. Sources enforce data permissions for the mapped account; OpenShell narrows destinations and supported request operations. HTTP method/path restrictions alone cannot prove SQL row/column limits or read-only semantics when queries use POST. Keep source-side roles authoritative.
6. Requiring data to stay near its source implies source-side query/action services for storage systems without their own compute. Authorized results still enter the agent and potentially its model context; this needs an explicit output boundary.

## First validation slice

Demonstrate one process, one mapped database account, one approved HTTP adapter, and one credential backend. Verify blocked alternative accounts/destinations, autonomous authorized reads/writes, credential rotation without exposing secrets, revocation behavior, and correlated source audit identity. Separately validate OpenShift security posture against the pinned upstream release.
